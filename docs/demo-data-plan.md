# 심사용 예시 데이터 설계안 (v2)

> **상태: 검토안. 아직 구현하지 않았습니다.**
> 현재 코드의 데모 프로필(A~D)은 그대로이며, 이 문서는 심사용 예시 데이터를 새로 만든다면
> 어떤 값이어야 하는지를 정리한 것입니다. 채택 여부는 팀에서 정합니다.

세 가지 산출물을 축으로 다시 짰다.

```
①  금융데이터 이상감지        ②  필수생활비 이체        ③  전문가 이양의뢰서
```

## 왜 19문항인가 — 실측으로 정했다

챕터를 하나씩 더해 가며 무엇이 나오는지 직접 돌려봤다.

| 조합 | 신탁설계서 | 후견설계서 | 이상거래 룰 |
|---|---|---|---|
| 코어만 (11문항) | **없음** | **없음** | 4개 |
| 코어 + 보호 (15) | 없음 | 없음 | **7개** |
| 코어 + 의료 (15) | **11개 조항** | **임의후견** | 4개 |
| **코어 + 의료 + 보호 (19)** | **11개 조항** | **임의후견** | **7개** |

**코어만으로는 의뢰서가 빈 껍데기가 된다.** 신탁도 후견도 안 나와서 확정된 지시사항이 0개다. 세 번째 축이 성립하지 않는다.

의료 4문항만 더하면 신탁 11개 조항과 임의후견 판정이 나온다. **상속 16문항은 넣지 않아도 된다.** 보호 4문항은 이상거래 룰을 4개에서 7개로 늘린다.

> **19문항.** 이전 설계안의 41문항에서 절반 이하로 줄었다. 상속과 투자 챕터를 뺐고, 세 축에 직접 기여하는 것만 남겼다.

**설정** — 의사능력 정상 / 금융사고 없음 / 코어 · 의료 · 보호 세 챕터 완료

## 축 ② 를 만드는 답변 — 코어 11문항

필수생활비 이체 설계가 여기서 나온다.

| 문항 | 질문 | 답변 |
|---|---|---|
| A09 | 매달 들어오는 돈 | **280만원** |
| A10 | 지금 바로 쓸 수 있는 돈 | **9,000만원** |
| A01 | 매달 반드시 나가는 돈 | 관리비·공과금 **32만원** / 통신비 **9만원** / 보험료 **38만원** / 정기 통원 **15만원** |
| A02 | 생활비는 매달 얼마면 | **190만원** |
| A03 | 생활비 지급 주기 | **매달 1일에 한 번** |
| A04 | 자동이체가 실패하면 | **예비계좌에서 자동으로 채워 결제** |
| A05 | 1회 이체 최대 금액 | **300만원** |
| A06 | 기본 차단할 거래 | 7종 전부 유지 |
| A07 | 이상 상황 시 알릴 사람 | **배우자 이정숙** |
| A11 | 12시간 무응답 시 다음 | **자녀 김도현** |
| A08 | 갑작스러운 큰 지출 | **의료예비계좌에서 집행** |

**여기서 나오는 산출물**

```
3층 계좌      생활계좌 · 의료예비계좌 · 보전계좌
자동이체      관리비 32만 · 통신 9만 · 보험 38만 · 통원 15만  = 월 94만원
정기지급      매달 1일 생활비 190만원
잔액 부족 시  예비계좌에서 자동 충당 후 알림
```

> **숫자를 이렇게 잡은 이유.** 수입 280만 − (고정비 94만 + 생활비 190만) = **매달 4만원 적자.** 자산 소진 차트가 완만하지만 분명한 기울기를 그린다. 흑자면 차트가 평평해서 볼 것이 없고, 적자가 크면 "이 사람은 이미 늦었다"로 읽혀 서비스 취지가 흐려진다.
>
> 즉시 가용 자금을 9,000만원으로 둔 것은 자산 규모를 낮춰 **고액자산가 전용 서비스로 보이지 않게** 하기 위해서다. 이 규모로도 신탁 판정과 소진 추정이 모두 정상 작동한다.

# 두 번째 프로필은 만들지 않기를 권한다

축 ③의 "시점을 놓치면 문서가 달라진다"를 보여주려면 진단받은 상태가 필요하다. 방법이 둘이다.

**방법 1 — 별도 프로필 없이 게이트에서 전환한다.** 심사위원이 `/start`에서 "진단받았습니다"를 고르면 김영수의 답변은 그대로 둔 채 의사능력만 바뀌어 문서가 전환된다. 관리할 데이터가 하나로 끝나고, **같은 사람의 같은 답변이 시점 때문에 다른 문서가 되는** 장면이라 대비가 오히려 선명하다.

**방법 2 — 79세 진단자 프로필을 따로 만든다.** 자산 규모와 생활비가 다른 인물을 하나 더 둔다. 다만 관리할 데이터가 두 배가 되고 이력 시드도 따로 맞춰야 한다.

**방법 1을 권한다.** 데이터가 하나면 랜딩 숫자와 설계서, 의뢰서가 모두 한 사람의 이야기로 묶이고, 심사위원이 직접 조작해 전환을 만들어 보는 편이 완성된 화면을 보는 것보다 설득력이 있다.

# 확인이 필요한 것 — 랜딩 숫자가 함께 바뀐다

새 랜딩의 숫자 섹션이 데모 프로필의 **실제 설계서를 돌려서** 값을 만든다. 하드코딩이 아니다.

```
현재  landingStats("B")  →  조항 22개 · 공백 1개 · 23년
```

김영수로 교체하면 이 숫자가 바뀐다. 코어 + 의료 + 보호 조합에서는 조항 18개 안팎에 **공백 0개**가 나올 전망이다.

공백이 0이라는 점을 짚어 둘 필요가 있다. 랜딩 문구가 *"당신의 설계서에는 지금 몇 개의 공백이 있습니까"* 인데 데모가 0을 반환하면 그 문장과 어긋난다. 선택지는 둘이다.

- **랜딩은 계속 기존 프로필을 쓰고, 김영수는 새 키로 추가한다**
- 김영수의 문항 하나를 비워 공백 1개를 만든다

**전자를 권한다.** 랜딩은 온보딩 카피에 맞는 숫자를 쓰고 심사용 데모는 완성된 상태를 보여주는 편이 각자의 목적에 맞는다. 다만 이 판단은 랜딩을 만든 사람과 함께 정하는 편이 좋겠다.
