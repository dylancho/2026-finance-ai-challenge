## 1. MVP 구현 범위

사용자가 스스로 금융 의사결정을 내리기 어려워질 상황에 대비해, **AI와 대화하며 자신의 결정
원칙을 정리하고 이를 조항 수준의 문서로 산출한 뒤, 그 문서가 실제 계약이 되기까지의 상태를
추적**하는 서비스입니다.

예선 MVP에서 실제로 동작하는 범위는 다음과 같습니다.

| 영역 | 구현된 범위 |
|---|---|
| 상황 입력 | 의사능력·금융사고 2문항으로 제도 가부를 먼저 판정 |
| 인터뷰 | 코어 11문항 + 선택 챕터 3종(투자 6 / 상속 16 / 의료 4), 6가지 입력 타입, 이전 질문 수정 |
| 설계서 산출 | 신탁설계서(제1조~제11조) · 후견설계서 · 지출설계서 3종 자동 생성 |
| 공백 관리 | 답하지 않은 항목을 조항 단위 공백으로 표시하고 해당 질문으로 딥링크 |
| 금융이력 | 10년치 합성 이력 적재, 성향 복제, 선언↔관찰 대조, 바이오마커 스코어링 |
| 전환 판정 | AI 경보 + 의료 증빙 2조건 게이트 |
| 시뮬레이션 | 시나리오별 조항 발동 추적, 30년 3구간 타임라인, 집행 근거 게이팅 |
| 전문가 연계 | 제출용 의뢰서 생성, 문서별 체결 상태 추적, 보호자 전달 |
| 이벤트 대응 | 생애 이벤트 3종에 대해 후보 3개 + "아무것도 하지 않음" 비교 |
| AI | 하이브리드 3계층 (룰 항상 실행 → 필요 시 LLM → 실패 시 룰 폴백) |

**본 문서는 위 범위만 기술하며, 미구현·향후 예정 기능은 포함하지 않습니다.**

### 2-10. 집행 근거 게이팅

## 4. AI 및 데이터 처리 방식

### 4-1. AI가 수행하는 역할

**3계층 구조로 나눕니다. 층마다 담당이 다릅니다.**

| 층 | 담당 | 하는 일 | LLM 없을 때 |
|---|---|---|---|
| **측정** | 룰 (순수 함수) | 중앙값·회귀 기울기·비율·이탈도 계산 | 동일 |
| **판정** | 룰 (설계 엔진) | 제도 가부, 신탁 유형, 후견 유형, 집행 가부 | 동일 |
| **서술** | LLM | 성향 해석, 대조 해석, 이벤트 트레이드오프 서술 | 템플릿 폴백 |

**측정층을 룰로 둔 이유** — 산술 결과를 LLM에 맡기면 같은 입력에 다른 숫자가 나옵니다. 심사 중
새로고침으로 수치가 바뀌면 그 자리에서 신뢰를 잃고, 단위 테스트도 불가능해집니다.

**LLM이 하는 일 (3개 엔드포인트)**

| 엔드포인트 | 모델 | 역할 |
|---|---|---|
| `POST /api/ai/parse` | Claude Sonnet 5 | 자유 입력에서 구조화 데이터 추출. 룰 신뢰도가 낮을 때만 호출 |
| `POST /api/ai/narrate` | Claude Opus 5 | 측정된 지표를 받아 성향 판단과 대조 해석을 서술 |
| `POST /api/ai/advise` | Claude Opus 5 | 이벤트 후보들의 트레이드오프를 서술 |

**LLM이 하지 않는 일** — 조항 본문 생성(설계 엔진이 결정론적으로 생성), 법 조문 생성(확인된
상수), 금액·문항 번호 산출, 제도 가부 판정, 집행 가부 판정.

세 엔드포인트 모두 **툴 콜 스키마를 강제**해 출력 형태를 고정하고, 숫자를 새로 계산하지 말고
받은 값을 인용하도록 지시합니다.

### 4-2. 사용 데이터 · 입력 / 출력

| 구분 | 데이터 | 저장 위치 |
|---|---|---|
| 선언 | 인터뷰 답변, 상황 입력 | `next.profile.v2` (브라우저) |
| 관찰 | 금융이력 월별 집계 · 매매 · 이상징후 | `next.ledger.v1` (브라우저) |
| 근거 | 문서별 체결 상태, 전달 대상 | `next.authority.v1` (브라우저) |
| 판정 원장 | 이벤트별 검토 후보 기록 | `next.decisions.v1` (브라우저) |
| 세션 | 목업 로그인 상태 | `next.auth.v1` (브라우저) |

**세 저장소를 끝까지 분리합니다.** 선언(말한 것)과 관찰(한 것)과 근거(집행할 수 있는 것)는
서로 덮어쓰지 않습니다. 합치면 "원래 뭐라고 했는지"가 사라져 대조가 성립하지 않습니다.

**LLM 엔드포인트 입출력**

| | 입력 | 출력 |
|---|---|---|
| parse | 사용자가 입력한 문장 1건, 질문 메타(id·타입·선택지) | 추출 항목 배열 |
| narrate | 이미 계산된 지표(위험회피도·손절선 등), 대조 항목 | 성향 판단 문단, 항목별 해석 |
| advise | 이벤트 종류, 계산된 후보 영향(소진 시점·노출액) | 후보별 트레이드오프 서술 |

세 경우 모두 **계산이 끝난 숫자만** 전송하며, 원본 거래 내역이나 개인 식별 정보는 보내지
않습니다.

### 4-3. 개인정보 · 민감정보 처리

- **실제 금융기관 API, 실계좌, 마이데이터를 사용하지 않습니다.** 금융이력은 시드 고정 합성
  데이터입니다.
- **서버에 아무것도 저장하지 않습니다.** 데이터베이스가 없습니다. 모든 입력은 브라우저
  localStorage에만 있으며, 브라우저를 지우면 사라집니다.
- **로그인은 목업입니다.** 상태 토글일 뿐 서버로 아무것도 보내지 않으며, 비밀번호를 받지
  않습니다.
- LLM 경로를 켠 경우, **해당 문장과 계산된 지표만** 파싱·서술을 위해 전송됩니다. 이름·연락처
  등을 입력하는 화면(전달 단계)의 값은 전송되지 않으며 화면에 명시되어 있습니다.
- 의료 증빙(진단서·장기요양등급)은 **첨부 여부와 발행일만** 다루며 파일을 업로드하지 않습니다.
- 화면과 문서 어디에도 **인지장애·치매 여부를 판정하지 않습니다.** "평소 금융 패턴과 달라진
  지점이 관측됩니다"까지만 쓰고 의학적 판정은 의료기관의 진단서에 맡깁니다.
- 공개 URL 보호를 위해 LLM 엔드포인트에 **호출 제한**을 두었습니다.

## 5. MVP 검증 방법

### 5-1. 확인 절차

**계정이 필요 없습니다.** 로그인 화면의 `로그인 없이 둘러보기`로 전 기능을 확인할 수 있습니다.

가장 빠른 확인은 **데모 프로필**입니다. 설문이 채워진 상태로 각 화면에 바로 진입합니다.

| # | 확인 항목 | URL | 예상 결과 |
|---|---|---|---|
| 1 | 설계서 3종 | `/plan?demo=B` | 신탁·후견·지출 설계서 탭. 신탁설계서에 제1조~제11조가 사용자 답변으로 채워져 있음 |
| 2 | 공백 관리 | `/plan?demo=B` 공백 목록 탭 | 의료비 지급 한도가 미설정으로 표시. 클릭 시 해당 질문으로 이동 |
| 3 | 대조 | `/plan?demo=B` 대조 탭 | "팔지 않기"라고 답했으나 하락 5회 중 5회 매도 — 모순으로 표시 |
| 4 | 금융이력 | `/ledger?demo=B` | 10년 스파크라인, 위험회피도·실효 손절선 등 측정 지표, 성향 판정 문단 |
| 5 | 제도 차단 | `/plan?demo=C` | **신탁설계서가 생성되지 않음.** 사유와 법정후견 경로, 즉시 가능한 계좌 보호 조치 제시 |
| 6 | 조항 발동 | `/simulation?demo=B` | 시나리오 진행. 미응답 항목에서 정지 노드 |
| 7 | **집행 근거 게이팅** | `/simulation?demo=B` 상단 토글 | 전부 끄면 1번 단계부터 잠김. 신탁만 켜면 대부분 흐르되 자동이체 단계가 반만 풀림 |
| 8 | 전환 게이트 | `/simulation?demo=B` 30년 축 → 2구간 | 바이오마커 경보 상태. 진단서를 첨부해야 발동 |
| 9 | **의뢰서** | `/referral?demo=B&step=2` | 문서번호·수신처, 조항별 근거 문항 번호, 참조 법령 조문 전문, 부록에 설문 응답 전 문항(미응답 포함) |
| 10 | 문서 전환 | `/referral?demo=C&step=2` | 제목이 「후견 청구 참고자료」, 수신처에 가정법원, 제출 주체가 보호자 |
| 11 | 이벤트 판정 | `/events?demo=B` | 이벤트 선택 시 후보 3개 + "아무것도 하지 않음"이 같은 단위로 비교됨 |
| 12 | 전체 흐름 | `/start` → 끝까지 | 계정 없이 처음부터 직접 입력 가능 |

**5분 핵심 경로** — 1 → 5 → 7 → 9 → 10.
설계서가 나오고(1), 늦으면 못 만들고(5), 만들어도 계약 전에는 집행되지 않으며(7), 그래서
전문가에게 넘기는 문서가 나오고(9), 시점에 따라 문서 성격이 바뀝니다(10).

### 5-4. MVP 단계의 제한사항

**데이터**

- 금융이력은 **시드 고정 합성 데이터**입니다. 실제 마이데이터·오픈뱅킹 연동은 인터페이스만
  정의되어 있고 연결되어 있지 않습니다.
- 서버·데이터베이스가 없어 **기기 간 동기화가 되지 않습니다.** 다른 브라우저에서 열면 처음부터
  시작합니다.

**실행**

- 실제 계약 체결, 자산 이동, 금융상품 가입, 후견인 지정을 **수행하지 않습니다.**
- 전문가·보호자에게 **실제로 발송하지 않습니다.** 전달은 문서 상태를 바꾸고 화면에 표시할
  뿐이며, 데모임을 화면에 명시했습니다.
- 문서의 체결 상태(`효력 발생`)는 앱이 판정하지 않습니다. 공증·등기·법원 심판·금융기관 등록처럼
  **앱 바깥에서 끝난 일을 알려주는 입력**이며, 시연을 위해 화면에서 전환할 수 있게 두었습니다.

**법적 효력**

- 생성되는 설계서와 의뢰서는 AI가 답변을 정리한 **초안이며 법적 효력이 없습니다.** 효력은
  전문가의 검토를 거쳐 신탁계약·후견계약 등 정식 절차가 체결됨으로써 발생합니다.
- 인용한 법 조문은 작성 시점 기준이며, 개정 여부와 사안 적용은 전문가 확인이 필요합니다.
- **유류분 관련 조문은 의도적으로 인용하지 않았습니다.** 2024년 헌법재판소 결정으로 내용이
  달라진 부분이 있어, 조문만 인용하면 현행과 어긋날 위험이 있기 때문입니다. 해당 사안은
  "전문가 확인 필요"로 표시합니다.
- 제시하는 절차의 기간·비용은 사건과 관할 법원, 금융기관에 따라 달라지며 일반적인 범위를
  참고용으로 정리한 것입니다. **확인되지 않은 수수료율은 숫자로 적지 않았습니다.**

**AI**

- LLM은 서술만 담당하며 판정하지 않습니다. API 키가 없거나 호출이 실패해도 룰 폴백으로 전
  구간이 동작하지만, **폴백은 동등한 대안이 아닙니다.** 화면 구조와 숫자는 유지되나 해석
  문장은 구간 분류 수준으로 격하됩니다.
- 공개 URL 보호를 위해 호출 제한을 두었으므로, 짧은 시간에 반복 호출하면 일시적으로 룰 폴백이
  표시될 수 있습니다.
- 회의 단계에서 검토했던 IRL·TFT·LSTM-Autoencoder 등 피처별 전용 모델은 적용하지 않았습니다.
  본 구현에서 실제로 도는 것은 **결정론적 지표 계산 + 파운데이션 모델 서술**이며, 화면에는
  "관측 지표"로 표기했습니다.

**범위**

- 가족이 대리해 설계하는 경로는 서비스 대상을 당사자 본인으로 한정하면서 **입력 화면에서
  제외**했습니다. 해당 상태의 산출물은 데모 파라미터(`?demo=C`)로 확인할 수 있습니다.
- 대리인 악용 방지를 위한 2차 인증, 프로필 변경 승인 로직은 구현하지 않았습니다.

- 이상거래 차단과 한도 축소는 위임 없이도 집행된다
- 답하지 않은 문항을 문서에서 감추지 않는다
- 근거가 없는 사항에 법 조문을 붙이지 않는다
