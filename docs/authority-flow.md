# 집행권한 축 (Authority) — 기술 및 흐름 정리

담당 김지훈 · 브랜치 `feat/authority-axis` · 2026-09-03

---

## 0. 이 모듈이 하는 일

> **설계서는 초안이고, 집행 권한은 체결된 계약서에서 나온다.**
> 그 사실을 앱 안에 **텍스트가 아니라 상태로** 만든다.

기존 서비스는 조항을 냈다. 그런데 그 조항을 실제로 집행하려면 신탁계약·후견계약이 체결되어
있어야 한다. 앱은 그 사실을 화면에 **문장으로만** 적어두고 있었고, 추적하지 않았다.

이 모듈은 두 가지를 만든다.

1. **신탁·후견 설계 의뢰서** — 설문 응답에서 조립해 은행 WM·법무법인에 제출하는 문서
2. **집행 근거 게이트** — 그 문서가 실제 계약이 되기 전까지 조항이 집행되지 않음을 추적

---

## 1. 전체 구조

```
[1. 설문 응답 (Profile)]        [2. 금융이력 (Ledger)]
        │ 22문항                        │ 월별 120레코드 + 매매 + 이상징후
        ▼                               ▼
[3. 설계 엔진 buildDesign()]    [4. 바이오마커 readBiomarker()]
        │ 신탁 11개조 / 후견 / 지출      │ 0~100 스코어 + 신호 5종
        │                               ▼
        │                       [5. 2조건 게이트 evaluateTrigger()]
        │                               │ AI경보(61+) + 최근1개월 진단서
        ▼                               ▼
   ┌────────────────────────────────────────────┐
   │  6. buildInstruments(profile, design)      │  ← 무엇을 체결해야 하나
   │     신탁계약 / 임의·법정후견 / 은행 위임장 │
   └────────────────────────────────────────────┘
        │                               │
        ▼                               ▼
[7. buildReferral()]            [8. canExecute(doc, ref, instruments)]
   의뢰서 조립                     조항별 집행 가능 여부
        │                               │
        ▼                               ▼
   /referral                    applyAuthority(scenarioResult)
   ①체결대상 ②의뢰서 ③전달          → /simulation 🔒 자물쇠 노드
```

**핵심:** 6번이 3·4·5번의 산출물을 읽기만 한다. 역방향 의존이 없어서 이 축을 통째로 들어내도
기존 기능은 그대로 돈다.

## 2. 단계별 세부 동작 흐름

### Step 1. 체결해야 할 문서를 파생한다 — `buildInstruments()`

설계 엔진이 이미 낸 판정을 읽어 "이 조항을 집행하려면 무엇이 체결되어야 하는가"를 만든다.
**새 콘텐츠를 쓰지 않는다.** 제도 가부 판정은 `trust.ts`·`guardianship.ts`가 이미 끝냈고,
같은 판단을 두 곳에서 따로 쓰면 반드시 어긋난다.

| 조건 | 산출 문서 | 효력 발생 시점 |
|---|---|---|
| `trust.available` | 신탁계약 | 계약 체결 + 신탁재산 이전 완료 시 |
| `verdict.code === "voluntary"` | 임의후견계약 | 가정법원이 임의후견감독인을 선임한 때 |
| `verdict.code` 법정후견 계열 | 후견개시 심판 | 심판이 확정된 때 |
| `capacity === "diagnosed"` | 신탁을 `unavailable` | — (법정후견 경로로) |
| 전 트랙 | 금융기관 대리인 지정 | 금융기관에 등록된 때 |

마지막 줄이 중요하다. 일상 트랙(A)에는 신탁도 후견도 없지만 지출설계서는 있다.
**"공과금 자동납부도 은행에 위임장을 내야 돈다"** 가 그 트랙의 유일한 집행 근거 장면이다.

### Step 2. 절차를 밟을 사람을 정한다 — `resolveActors()`

시점은 서류의 성격만 바꾸는 게 아니라 **실행 주체**도 바꾼다. 진단을 받은 뒤에는 본인이
공증사무소에 가서 계약을 맺는 장면 자체가 성립하지 않는다.

```
actsAlone(p) = subject !== "family"
             && capacity !== "diagnosed"
             && capacity !== "incident"
```

`false`면 `by: "본인"` 단계가 전부 `보호자`로 바뀌고 이유가 붙는다.

> ⚠️ 본인의 의사능력이 충분하지 않은 상태에서 한 행위는 나중에 효력이 다투어질 수 있습니다.
> 후견개시 심판은 **본인, 배우자, 4촌 이내의 친족, 검사 또는 지방자치단체의 장**이
> 청구할 수 있습니다 (민법 §9·§12·§14-2).

법원·전문가·금융기관 단계는 원래 본인이 하는 일이 아니므로 손대지 않는다.

### Step 3. 의뢰서를 조립한다 — `buildReferral()`

**설문 응답에서 조립한다. 조항 본문을 새로 쓰지 않는다.** `buildTrustDesign()`이 이미
결정론적으로 낸 문장을 그대로 인용한다. 여기서 다시 만들면 `/plan` 화면과 제출 서류가
어긋나고, 심사 중 두 화면을 나란히 놓고 비교당하면 그 자리에서 끝난다.

| § | 내용 | 출처 |
|---|---|---|
| 표지 | 문서번호 · 수신 · 제출 주체 · 응답 문항 수 | `docNumber()` · `recipients` · `executor` |
| 1 | 의뢰 개요 · 주거래 금융기관 | `profile` + `trustContact(ledger)` |
| 2 | 금융이력 이상 탐지 기록 | `reading` + `gate` (있을 때만) |
| 3 | 재산 및 관계 현황 | 금액 붙은 `multi` 응답 → 표 |
| 4 | 확정된 지시사항 | `trust.clauses` 중 `status !== "missing"` |
| 5 | 미확정 사항 | `findGaps()` 재사용 |
| 6 | 절차 · 요건 · 비용 | `roadmap` + `cost` |
| 7 | 참조 법령 | `statutesFor()` — 확인된 조문만 |
| 8 | 고지 | 모드별 고정 문구 |
| **부록 A** | **설문 응답 원문 전 문항** | `activeQuestions()` — **미응답도 싣는다** |

§4의 각 조항에 근거 문항 번호가 병기된다.

```
제5조  정기지급                                    [B07 · B08]
  ① 수탁자는 수익자에게 매월 300만원을 매월 1회 지급한다.
  ② 수익자가 요양시설에 입소한 때에는 월 180만원을 증액하여 지급한다.
```

부록 A가 이 문서를 **상담 메모가 아니라 인수인계 문서로** 만든다. 전문가가 지시의 출처를
역추적할 수 있고, 나중에 다투어질 때 원본 답변으로 돌아갈 수 있다.

### Step 4. 시점이 서류의 성격을 바꾼다

```
delegated = !actsAlone(profile) || gate.fired === true
```

| | contract | petition |
|---|---|---|
| 조건 | 의사능력 정상 | 진단 응답 **또는** 2조건 게이트 발동 |
| 제목 | 신탁·후견 설계 의뢰서 | 후견 청구 참고자료 |
| 수신 | 하나은행 WM·신탁부서 / 법무법인 | 가정법원 / 후견인 후보자 / 법무법인 |
| 제출 주체 | 본인 | 보호자 |
| §4의 성격 | 계약 조항 초안 | 법원과 후견인에게 전달할 **본인의 사전 의사** |

> **미리 했으면 계약서가 되고, 늦었으면 법원에 낼 근거가 남는다. 어느 쪽이든 빈손이 아니다.**

`reading.band === "alert"`를 **직접 보지 않는다.** 그러면 2조건 게이트를 우회해
**AI 경보만으로 사람의 법적 지위를 바꾸는** 셈이 된다. `evaluateTrigger()`의 결과만 읽는다.

### Step 5. 집행 근거를 판정한다 — `canExecute()`

```ts
canExecute(doc: DocKey, ref: string, instruments: Instrument[]): ExecutionCheck
```

규칙은 셋뿐이다.

1. `covers`에 걸린 문서가 없으면 **통과** — 집행 근거가 필요 없는 조항
2. 걸렸고 그 문서가 `effective`면 **통과**
3. 그 외 전부 **차단**

`covers` 배선이 정밀도를 만든다.

```
신탁계약        covers: ["trust:*"]
후견계약        covers: ["guardianship:*"]
은행 위임장     covers: ["expense:§2", "expense:§6"]   ← 대행이 필요한 항목만
```

**지출설계서 전체를 위임장에 묶지 않는다.** `expense:*`로 덮으면 이상거래 차단(§4)과
한도 축소(§3)까지 잠기는데, 그 둘은 위임 없이 지금 당장 신청할 수 있고 **신탁이 막힌
사용자에게 서비스가 바로 그것을 권한다.** 잠그면 그 안내가 거짓말이 된다.

> **함정.** 시나리오가 내는 ref에는 항 번호가 붙는다 — `"제5조 ②"`.
> `normalizeRef()`로 머리만 떼어 비교하지 않으면 그 노드가 어떤 문서에도 안 걸려
> **조용히 통과한다.** 게이트가 있는데 안 막히는 최악의 실패다.

### Step 6. 시나리오에 덧씌운다 — `applyAuthority()`

`lib/design/scenario.ts`(938줄)는 **수정하지 않는다.** 조항이 무엇을 하는지는 그쪽이 이미
계산했고, 여기서는 "그것을 집행할 근거가 있는가"만 덧씌운다. 두 판단을 한 파일에 섞으면
시나리오를 고칠 때마다 게이트가 함께 흔들린다.

```
ScenarioNode.status:  "ok" | "gap" | "noauthority"
                                       ↑ 추가
```

**`gap` 노드는 덮어쓰지 않는다.** 안 채운 칸과 집행할 수 없는 칸은 해결 방법이 다르다.

## 3. 공백의 세 종류

이 축이 붙으면서 완성된 구조.

| 상태 | 의미 | 해결 방법 |
|---|---|---|
| `gaps` | 안 채운 칸 | 질문에 **답하기** |
| `contrast` | 채웠는데 사실과 어긋나는 칸 | 선언/이력 중 **고르기** |
| **`noauthority`** | **채웠는데 집행할 수 없는 칸** | 전문가와 **체결하기** |

## 4. 데모 시나리오 — 두 박자

`/simulation?demo=B` 상단 「집행 근거」 토글로 시연한다.

```
1박  전부 초안
     🔒 ① 치매 진단          trust:제4조     집행 근거 없음
     🔒 ② 발동 확인          trust:제4조 ②
     🔒 ③ 생활비 자동 지급   trust:제5조 · expense:§2
     🔒 ④ 투자자산 처리      trust:제7조
     🔒 ⑤ 부동산 매각 시도   trust:제8조
     → 설계서 완성도 91%, 집행 0건

2박  신탁만 체결 (trust: effective / bank_mandate: draft)
     ✓  ① ② ④ ⑤ 흐름
     ◐  ③ 신탁 제5조는 지급됨 / 🔒 expense:§2 자동이체는 위임장 없어 수동
```

**③이 반만 잠기는 게 이 축의 정밀도다.** 문서마다 `covers` 범위가 달라 한 노드 안에서도
조항별로 잠김이 갈린다. 전부-아니면-전무보다 설득력이 있고, 서비스가 말하는 3단계 권한
체계(AI 독자 / 보호자 동의 / 법적 후견인)가 화면에서 분리되어 보이는 지점이다.

> 초안 상태에서는 **①부터** 잠긴다. 신탁계약이 없으면 제4조 트리거 자체가 성립하지 않는다.

## 5. `/referral` 진입점 5개

| # | 위치 | 문구 | 언제 보이나 |
|---|---|---|---|
| 1 | `/plan` 하단 CTA 밴드 | 전문가에게 전달할 의뢰서 만들기 | 항상 |
| 2 | `/simulation` 집행 근거 토글 바 우측 | 의뢰서 보기 → | 항상 |
| 3 | `/simulation` 🔒 잠긴 노드 안 | 전문가에게 전달할 의뢰서 만들기 → | 미체결 상태 |
| 4 | `/simulation` 우측 사이드 박스 | 집행 근거 N건 만들러 가기 | 잠긴 단계가 있을 때 |
| 5 | `/simulation` 30년 타임라인 게이트 카드 | **이 기록으로 의뢰서 만들기 →** | **트리거 발동 시** |

**5번이 이 담당의 시작점이다** — *"금융 활동에 이상이 생겼을 때"*.

```
/simulation?demo=B
  → Phase 2 선택 → 「전환 게이트」 카드
  → 바이오마커 80점 · 경보          (시드 B 실측값)
  → 진단서 첨부                      ← 이걸 눌러야 2조건 충족
  → "전환 발동" + 링크 노출
  → /referral 이 「후견 청구 참고자료」를 냄
```

진단서가 없으면 링크 대신 이렇게만 뜬다.

> ☐ 최근 1개월 이내 의사 진단서 또는 장기요양보험 등급 발행서가 필요합니다

**같은 페이지가 상태에 따라 두 종류 문서를 낸다.** 1~4번으로 들어가면 「신탁·후견 설계
의뢰서」, 5번으로 들어가면 「후견 청구 참고자료」.

## 6. 참조 법령 — 확인된 조문만

앱은 이미 법적 사실을 화면에서 단정하고 있었다. 근거가 없었을 뿐이다.

| 앱의 기존 주장 | 근거 |
|---|---|
| 후견계약은 공정증서로 | 민법 §959-14② |
| 감독인 선임으로 효력 발생 | 민법 §959-14③ |
| 등기가 선행되어야 함 | 민법 §959-15① |
| 성년 / 한정 / 특정후견 | 민법 §9① / §12① / §14-2①② |
| 신탁 설정 방법 | 신탁법 §3① |
| 유언대용 / 수익자연속 | 신탁법 §59② / §60 |

**원칙 셋.**

1. **조문 전문을 그대로 싣는다.** 요약하면 그 요약이 우리 주장이 되고 인용이 아니게 된다.
2. **유류분(민법 §1112 이하)은 넣지 않는다.** 2024년 헌재 결정으로 달라진 부분이 있어
   조문만 인용하면 현행과 어긋난다.
3. **명문 근거가 없는 것에는 붙이지 않는다.** "의사능력 없는 자의 법률행위는 무효"는 판례
   법리이고 민법에 그 문언이 없다. 금융기관 대리인 지정도 약관·내규의 영역이다.

> **얕은 인용은 인용이 없는 것보다 나쁘다.** 틀린 조문 하나가 나머지 전부를 의심하게 만든다.

같은 이유로 **신탁보수 요율을 숫자로 적지 않는다.** 공시가 "신탁계약으로 정함"이므로 그대로
적고, 최저 수탁금액만 확인된 두 지점을 나란히 싣는다 — KB 간편형 유언대용신탁 1,000만원
(2025.7) / 하나 Living Trust 5억원 이상. **50배 편차가 이 시장의 실제 모습이다.**

## 7. 금융데이터의 쓸모 — 진단이 아니라 연결

주거래 금융기관을 **설문에서 묻지 않는다.** 물어보면 대개 부정확하고, 이력에는 그대로 남는다.

```
§1  주거래 금융기관   하나은행 (거래 비중 62%)
    판단 근거        고정비 자동이체와 입출금이 거친 기관의 비중.
                     설문 응답이 아닌 금융이력 관찰값입니다.
```

주거래에 신탁 창구가 없으면(인터넷은행 등) 다음 기관을 제안하고 **그 사실을 밝힌다.**
조용히 바꾸면 왜 그 은행인지 알 수 없다.

```
§1  주거래 금융기관   카카오뱅크 (거래 비중 55%) — 신탁 창구를 두지 않는
                     기관이므로 KB국민은행 신탁부서를 제안합니다
```

회의에서 치매 진단 기능을 제외하기로 한 결정과 방향이 같다. 금융데이터는 **판정**이 아니라
**연결**에 쓴다.

### 상태 저장소 3개를 분리한다

| | Profile | Ledger | **Authority** |
|---|---|---|---|

## 9. LLM을 붙일 자리와 붙이면 안 되는 자리

현재 이 축에 LLM 호출은 하나도 없다. 붙인다면 `/api/ai/referral` 하나이고,
기존 `/api/ai/parse`·`/api/ai/narrate`와 같은 규약을 쓴다 — **키 없으면 204 → 룰 폴백.**

| | LLM |
|---|---|
| §1 의뢰 취지 문단 | ✅ |
| §5 각 미확정 항목의 "안 정하면 무슨 일이 생기나" 서술 | ✅ |
| **§4 조항 본문** | ❌ 설계 엔진이 이미 냈다. 다시 만들면 `/plan`과 어긋난다 |
| **§7 참조 법령** | ❌ 확인된 상수다. 생성하게 두면 조문 번호를 지어낸다 |
| **금액 · 문항 번호** | ❌ |

프로바이더는 레포 통일성상 `@anthropic-ai/sdk`를 따르고 있다. 제미나이로 바꾸려면
라우트 파일 하나만 갈면 되고 출력 스키마는 유지된다.

## 10. 표현 원칙

- **앱은 권한을 만들지 않는다.** 화면 어디에도 "승인 완료"·"권한 부여"라고 쓰지 않는다.
- **`effective`로의 전환은 앱 안에서 일어나는 일이 아니다.** 토글 옆에 명시한다 —
  *"체결 여부는 이 화면에서 정해지지 않습니다. 공증·등기·법원 심판·금융기관 등록처럼
  앱 바깥에서 끝난 일을 여기에 알려주는 것입니다."*
- **진단하지 않는다.** 탐지 기록에도 인지장애·치매 여부를 쓰지 않는다.
  *"평소 금융 패턴과 달라진 지점"* 까지만 쓰고 의학적 판정은 첨부된 진단서에 맡긴다.
- **미응답을 감추지 않는다.** 빈칸을 감추면 문서가 완성된 것처럼 보이고,
  그 상태로 계약이 체결된다.
